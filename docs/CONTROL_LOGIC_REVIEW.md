# 0.7 控制逻辑复盘与修复

## 结论

用户的曲线已成功应用，但旧版执行链把曲线结果覆盖了。主因不是 EC 写入失败：

1. 曲线使用“升温立即跟随、降温累积平滑”的隐藏温度，不一定是界面所示采样温度。
2. 低于最低运行输出的曲线结果会按停转量化。
3. 停转达到上限后 stopCooling 锁存到上限减 5°C；另有 lowCooling、hotCooling 独立锁存。
4. 界面只显示最终目标 30% 和笼统“静音补风”，未显示原始请求和解除条件。
5. 主控与独立看护还各自写了一套温度门限，最低输出配置变化可能造成不同判断。

因此“允许停转，50°C 上限”实际变成了“补风后先降到 45°C 才能恢复”，与用户界面及预期不符。
反复应用只重置历史状态，不能根治这个执行链冲突。

## 0.7 的唯一执行顺序

| 优先级 | 输入 / 条件 | 行为 |
|---|---|---|
| 最高：故障恢复 | CPU ≥95°C、无效传感器、失联、真实失速等 | 主控/看护恢复固件自动；需用户重新应用 |
| 正常请求 | 当前采样温度 + 曲线，或百分比 / RPM 模式 | 得到请求百分比；曲线不再使用隐藏温度累积器 |
| 停转 / 最低输出 | 请求低于最低输出，且允许停转、低于停转上限、不是正 RPM 目标 | 目标为 0%；否则目标至少为最低输出 |
| 温度最低输出 | 当前温度达到停转上限 | 至少为用户设定的最低运行输出，而不是固定抬至 30% |
| 温度最低输出 | CPU ≥60°C | 至少为 max(30%, 最低运行输出) |
| 温度最低输出 | CPU ≥80°C | 满速 100% |
| 有界启动 | 非零目标且任一风扇实际为 0 RPM，且本次启动尚未助推 | 100% 最多 3 秒；之后回目标。请求重新满足停转条件时立即取消助推 |

温度下限是按当前温度直接计算的纯函数，没有 stopCooling / lowCooling / hotCooling 锁存。
低于门限后，在下一次约 0.5 秒控制采样时重算；不要求额外降低 5°C，也不把正常调整锁成故障。
软件响应不等于风扇物理转速瞬时改变，固件、惯性和 PWM 量化仍然存在。

主控与看护共用 ThermalLimits.MinimumOutput，并在 ownership ticket 中传递停转上限和最低运行输出。
看护只在实际目标持续 3 秒未满足这个同一规则时恢复自动，温度紧急保护不等待这个超时。
0% 请求下长期 0 RPM 不算失速；非零运行时连续 0 RPM 才检查主控 8 秒 / 看护 12 秒失速。

## 用户案例

当前曲线 `35:0;45:10;55:20;65:30;75:40;80:100`，最低运行输出 20%，停转上限 50°C：

| 当前温度 | 曲线请求（整数化） | 正常执行目标 | 原因 |
|---|---:|---:|---|
| 47.9°C | 13% | 0% | 低于最低运行输出，且低于停转上限，允许停转 |
| 50°C | 15% | 20% | 达到停转上限，至少按最低运行输出执行 |
| 59°C | 24% | 24% | 直接按曲线，无隐藏的 30% 保持 |
| 60°C | 25% | 30% | 显式的 60°C 输出下限 |
| 79°C | 88% | 88% | 直接按曲线，无隐藏的 100% 保持 |
| 80°C | 100% | 100% | 达到满速门限 |

上表不包括从真实停转启动时至多 3 秒的启动助推；该状态会独立显示。
47.9°C 的结果不再取决于之前是 50、64.9 还是 80°C。

## 界面、配置、验证边界

- 状态卡显示请求百分比、执行目标百分比、实际调整原因，风扇表仍显示真实 RPM / 实际 PWM。
- 控制决策与同帧显示的温度采用同一个采样，避免一次控制循环内二次读温造成“温度与请求对不上”。
- 停转上限明确标注“即刻”，60/80/95°C 固定规则直接显示，额外回差已移除。
- 既有配置字段与节点保留，不清空、不静默改写用户文件；保存及重启不自动接管硬件。
- 无隐藏回差意味着阈值附近可能反复启停。可通过合理的停转上限与节点减少切换；没有用另一套隐藏锁存去掩盖它。
- 离线回归覆盖原始案例、冷热历史、50/60/80/95°C 边界、35–60°C 所有停转上限与最低输出 10/20/40% 的双向温度扫描、主控/看护一致性、启动中回到停转、UI 请求/目标/原因及持久配置。
- 本次不把模拟测试当成物理停转或 95°C 高温实测。没有故意加热、取消固件保护或绕过 UAC。
